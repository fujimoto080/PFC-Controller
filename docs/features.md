# PFC Balance 機能ドキュメント

## 1. アプリ概要

PFC Balance は、**タンパク質（P）・脂質（F）・炭水化物（C）・カロリー**の記録と目標管理を行うアプリです。日次・週次・月次で摂取状況を可視化し、食品辞書やバーコード連携で入力効率を高められます。

---

## 2. 画面一覧（主要導線）

下部ナビゲーションから次の画面へ遷移できます（中央はバーコードスキャン）。

- **今日**（`/`）
- **提案**（`/suggest`）
- **設定**（`/settings`）

設定画面の「登録データ」から開く画面:

- **食品リスト**（`/foods`）
- **バーコード一覧**（`/barcodes`）
- **商品カタログ**（`/catalog`）: 組み合わせ提案 API が使う `data/<店舗 ID>.json` の中身を、お店ごとにカテゴリで折り畳んで一覧する。商品名から公式の商品ページを開ける
- **利用状況**（`/usage`）

設定画面の「フィードバック」で、タイトルと内容を送ると GitHub Issue として起票される（`POST /api/feedback`、`lib/server/github-issues.ts`。環境変数 `GITHUB_ISSUE_TOKEN` が必要）。

補助ページ:

- **プライバシーポリシー**（`/privacy-policy`）

## 3. ホーム（ダッシュボード）機能

### 3.1 日次PFCダッシュボード

- 当日または任意日の摂取量（kcal / P / F / C）を表示
- 目標値に対する進捗をプログレス表示
- 左右ボタンおよびスワイプで日付移動
- 今日以外の日付も確認可能

### 3.2 毎日の栄養目標と週平均

- プロフィールから目標を共通計算する。減量の赤字は維持カロリーの20%まで、既定の最低カロリーも守る
- Pは体重×1.6g（カロリーの40%まで）、Fは25%、Cは残りから計算し、カロリーと整合させる
- カロリーは±5%、Fは20〜30%を目安として表示。Pは確保する目標、F/Cは目安
- カロリー超過を翌日から7日間に分散。減額は基本の5%・100kcal/日まで、総赤字25%と既定の最低カロリーを守る。P/Fは固定、Cだけ再計算
- 過去の超過は実際の基本目標との差で相殺し、調整額を架空の返済として引かない。不足の先取り・PFC別の繰越・チートデーは無し
- 未記録日と最低カロリー未満の記録は相殺に使わない。記録漏れを判定できないため完全な食事記録が必要
- 超過は7日で調整を終了。下限や減額上限で調整できない分を無理に返済しない
- 運動は活動レベルに含め、運動記録を食事枠へ加算しない
- 前日まで7日間の記録日平均と記録日数を表示。未記録日は平均から除く
- 提案は残りカロリー内でPを優先し、F/Cを埋めるだけの追加食を求めない

### 3.2.2 文章からの AI 記録

- サマリーの直下に入力欄があり、「おにぎり2個とサラダ」のように書いて送信すると AI が栄養値を推定する
- 推定結果は確認画面（数量 ×0.5〜×2 を選んで 1 タップで記録、または修正して記録）で開く
- 追加シートの検索欄に入れた文字も「「○○」をAIで推定」ボタンからそのまま推定できる

### 3.3 よく使う食べ物（クイック追加）

- お気に入り登録した食品を横並びボタンで表示
- ワンタップで現在時刻の記録として追加

### 3.3.0 食べたもの一覧

- 選択日の記録を朝ごはん・昼ごはん・晩ごはんに分け、枠ごとの合計 kcal と一緒に時刻順で表示する（`lib/meal-schedule.ts` の `assignMealSlots`）
- 前の記録から 1 時間以内の記録は同じ 1 回の食事にまとめる
- 食事の順番は朝→昼→夜を逆戻りさせず、時間帯（〜10時 朝・〜15時 昼・以降 夜）からの外れと同じ枠への詰め込みが最も少なくなるように割り当てる。10:30・13:00・19:00 の 3 回なら 10:30 は朝、10:30・19:00 の 2 回なら 10:30 は昼になる

### 3.3.1 運動記録

- 設定画面で登録したスポーツ（名前と1回あたりの消費 kcal）を横並びボタンで表示し、ワンタップで選択日に記録
- 記録した運動は一覧表示し、個別に削除できる
- 消費カロリー分だけその日のカロリー上限が増える（上限表示に「運動 +○」を併記）
- スポーツは消費の単位 METs だけを設定画面の「スポーツ」に登録し、記録のたびに強度（軽め0.75・普通1・きつめ1.25）と時間(分)を指定すると、METs × 強度 × 体重 × 時間 × 1.05 で消費カロリーを計算する
- スポーツの登録・削除は設定画面の「スポーツ」から行う（`PUT /api/sports` で一覧ごと保存）
- スマホのヘルスケア連携（Android の Health Connect）の活動消費は `PUT /api/health-sync` で 1 日 1 件に上書き同期される（`HEALTH_SYNC_TOKEN` の Bearer 認証。0 kcal なら削除）。運動記録の一覧には「ヘルスケア連携（活動消費）」として出る

### 3.4 週平均サマリー

- 過去7日間の平均摂取量（kcal / P / F / C）を表示
- 日次目標に対する平均進捗を可視化

### 3.5 目標編集（自動計算対応）

- 設定アイコンから目標編集ドロワーを開く
- プロフィール入力により目標PFCを自動計算
- 計算後の目標は変更すると自動で保存（設定画面の各項目は保存ボタン不要。入力が止まって約0.8秒後、または画面を離れたときに保存し、カード右上に「保存中…／保存済み」を表示。入力途中の不正な値は保存しない）

## 4. 追加画面（食事登録）機能

### 4.1 基本入力

- 食べた**日付・時刻**を指定して登録
- 食品名、P/F/C、カロリー、店名を入力
- 必要に応じて食品辞書へ同時保存

### 4.2 バーコード読み取り・まとめて記録

- 下部ナビ中央の「スキャン」でカメラを開き、閉じずに商品を次々に読み取って一覧に溜める
  - 同じバーコードを読むと数量が +1。かざしたままの同じ商品は 2.5 秒間は数えない
  - 映像内のシャッターで成分表示をその場で撮ると、写っている商品（複数可）をまとめて AI で読み取って加える（カメラアプリに切り替えないのでページが破棄されない）
  - 撮影方法は「写真」（ImageCapture の `takePhoto` で静止画を撮る。高解像度で撮影用のピント合わせも効く）と「映像」（映っているフレームを切り出す）を切り替えられる。既定は写真で、選んだ方法は localStorage に保存する。ImageCapture 非対応の端末（iPhone の Safari など）は映像のみ
  - カメラ画面右下のボタンから保存済みの画像を選んで、撮影と同じように読み取らせることもできる
  - 未登録のバーコードは「未登録」として残し、確認画面で成分表示の撮影か手入力で埋める
  - BarcodeDetector 非対応のブラウザでも、番号入力と撮影は使える
- 確認画面で各商品の修正・数量（0.5 刻み）・合計 PFC を確認し、一括で保存する
  - 「食べた記録にも追加する」オン: 指定日時の食事として記録。オフ: 食品リストへの登録とバーコードの紐付けだけ
  - どちらの場合も、同じ内容が無い食品は食品リストへ追加し、未登録だった・直したバーコードには食品情報を紐付ける
  - 商品の修正中に成分表示を撮り直して読み取り直せる（読み取りに失敗したら元の内容に戻す）
  - 写真から読み取った商品は、修正中に「写真を足す」で商品名などの別の面を撮ると、前に読み取った写真と合わせて最大3枚で読み取り直す（後の写真だけで値を上書きしない）。読み取った写真はメモリにだけ持ち、一覧の保存には含めない
  - 保存ボタンの帯は画面下に固定するが、商品の修正中は保存できずキーボードと入力欄の間に挟まるため固定しない
  - 撮影済みの写真を複数選んで追加することもできる
- 一覧は localStorage に保存し、閉じても続きから再開できる。確認待ちの件数をスキャンボタンにバッジで表示
- JAN/EAN/UPC/ITF/Code128 等に対応
- チェックデジット検証で不正読み取りを抑制
- カメラは連続オートフォーカスで起動し、映像をタップするとその位置にピントを合わせる（3 秒後に連続オートフォーカスへ戻す）。ズームのスライダーとライトのボタンも出す。いずれも端末が対応している場合だけ（主に Android の Chrome。iPhone の Safari は非対応）。実装は `lib/client/camera.ts` と `components/scan/CameraControls.tsx`
- AI に送る写真は長辺 2048px の JPEG に縮小する
- 確認画面と写真の自動入力ボタンの下に「写真の読み取り結果を確認」を出し、直近 10 件の読み取りについて送った画像（解像度・サイズ）・AI の応答テキスト・読み取れた食品を確認できる（応答はコピー可）。画像が大きいためメモリにだけ持ち、再読み込みで消える（`lib/client/ai-readings.ts`）
- AI の読み取り・推定で P/F/C/カロリーが全部 0 の結果は使わない（複数読み取りでは除き、1件の読み取り・推定ではエラーにする。`lib/pfc.ts` の `hasNutrition`）

### 4.3 バーコードマッピング参照・登録

- コード入力で既存マッピングを照会
- マッピングがあればフォームへ自動反映
- 記録時、該当バーコードへ食品情報を保存可能
- 設定画面からバーコード一覧ページへ遷移できる

### 4.4 AI補助入力

- 栄養成分表示を撮影すると、OpenAI API で表示のP/F/C・カロリー・商品名・メーカーを直接読み取る
  - 応答は OpenAI の Structured Outputs（zod スキーマから作る JSON Schema）で形を固定し、同じスキーマで検証する。形式どおりでない応答は読み取れなかったものとして扱う
  - 食品ごとに判断の根拠（どの記載から読んだか・換算や推定の計算）も `evidence` として答えさせ、「写真の読み取り結果を確認」の応答テキストで見られる。食品の値には使わない
  - 不鮮明でも値を 0 にせず最も妥当な値を入れさせ、代わりに値の確かさ（`confidence`: high / medium / low）を答えさせる。high 以外があれば数値の確認を促すトーストを出し、「写真の読み取り結果を確認」の読み取れた食品に確かさを出す。0 にしてよいのは表示に 0 と記載されている場合だけ。読み取った値は記載どおりの桁で入れさせ、整数に丸めさせない
  - 撮影ボタンの隣の「画像」から保存済みの画像を選んで読み取らせることもできる
  - 成分表示と商品名が別の面にある商品のため、写真は最大3枚まで溜めてから1回でまとめて読み取れる（撮影・選択した写真はサムネイルで確認・外せる。クイック入力の画像ボタンは選んだ複数枚をそのまま送る）。複数枚は同じ1つの商品として1件にまとめる
  - 読み取った後も写真は残し、写真を足すと前の写真と合わせて読み取り直す（成分表示を読んだ後に商品名の面を撮っても PFC が上書きされない）。写真を足す・外すまでは「読み取り済み」として同じ組を読み取り直させない
  - 商品名には「（推定）」などの但し書き・注釈を付けさせない（テキスト推定も同様）。推定・不確かさは `evidence` / `confidence` で表す
  - 1包装・1食あたりの値を優先し、100gあたりの表示のみなら内容量で換算
  - 成分表示が写っていない料理写真は、写っている量から推定
  - 食品リストの新規追加・編集画面でも利用可能（店内グループは入力済みの値を保持）
- 食べた内容をテキストで入力し、OpenAI API（Web 検索付き）でP/F/Cとカロリーを推定
- 結果を入力フォームへ反映し、そのまま保存可能

## 8. 目標自動計算（プロフィール連動）

プロフィール項目:

- 性別
- 年齢
- 身長
- 現在体重
- 目標体重
- 活動レベル

目標期間（月）は入力不要で、推奨期間（減量でなければ3ヶ月）から自動で決まります。

計算の考え方:

- BMR（基礎代謝）を算出
- 活動レベルからTDEE（維持カロリー）を算出
- 目標体重・期間から1日あたり調整カロリーを算出
- 最低安全カロリー（男性1500 / 女性1200）を下限適用
- 推奨PFCを表示
- 5%ルール等を使った推奨減量期間の目安表示

## 9. バーコード連携機能

### 9.1 API（要ログイン）

- `GET /api/barcode?code=...` : バーコードから食品情報を取得。登録が無ければ商品カタログ（11.4）の JAN コードで探し、店名にはお店・メーカー名を入れる（どちらにも無ければ 404）
- `POST /api/barcode` : `{ barcodes: string[], food }` でバーコードへ食品情報を保存
- `GET /api/barcode/mappings` : 登録済みマッピング一覧
- `POST /api/ai-nutrition/image` : `{ imageDataUrls }`（最大3枚、同じ商品の別の面）から栄養成分表示（または料理）を 1 件の食品として読み取る
- `POST /api/ai-nutrition/image/items` : `{ imageDataUrls }` の 1 枚の写真に写った複数の商品の栄養成分表示を読み取る
  - どちらも `{ foods, response }` を返す。`response` は AI の応答テキストそのもの。読み取れなければ `foods` は空配列（エラーにしない）

### 9.2 永続化

- Upstash Redis を使用してバーコードマッピングを保存
- 追加済みバーコードはインデックス管理し一覧取得可能

### 9.3 管理画面

- `/barcodes` で登録済みのバーコードと食品名・店名・PFC情報を一覧表示

## 10. データ保存・同期仕様

### 10.1 サーバー保存

- 食事記録・運動記録・食品辞書・設定・スポーツマスタは Postgres にユーザー単位で保存
- 起動時に `GET /api/user-data` で全データを取得する

### 10.2 クライアントストア（`lib/client/store.ts`）

- 取得データは不変オブジェクトとして保持し、`useSyncExternalStore` で各画面が購読する
- 更新操作（`lib/client/actions.ts`）は楽観的に即時反映し、API 失敗時はロールバックしてエラートーストを表示
- 起動を速くするため `localStorage`（`pfc:cache:v4:<userId>`）にキャッシュし、次回起動時に即時表示した後サーバーの最新で置き換える

### 10.3 その他のローカル保存

- `pfc_add_food_form_draft`（追加フォームの入力途中データ）
- `pfc_manage_foods_collapsed`（食品管理画面の折りたたみ状態）

### 10.4 利用状況の記録

- 使われていない機能を見つけるため、画面表示・クリックした操作・日付移動のスワイプ・MCP のツール呼び出しを `pfc_usage_events` に記録する
- クライアントは `components/layout/UsageTracker.tsx` がクリックを拾い、5 秒ごと・画面を離れるときにまとめて `POST /api/usage-events` へ送る
- 操作名は `data-track` > `aria-label` > 表示テキスト > アイコン名 の順に決める（`lib/client/usage.ts`）。食品名など中身で変わるボタンには `data-track` で固定の名前を付ける
- 設定画面「登録データ」の「利用状況」（`/usage`）で、種類ごとに回数と最後に使った日時を多い順に表示する

## 11. ChatGPT 連携（MCP サーバー）

### 11.1 MCP ツール

- `/api/mcp` で Streamable HTTP の MCP サーバーを提供（`mcp-handler`）
- `get_nutrition_status` : 指定日（既定は今日, JST）の上限（目標 + 運動消費 − 繰越。アプリの表示と同じ）・摂取済み・残り・食べた物・運動・プロフィール
- `get_meal_history` : 今日を含む直近 1〜31 日の食事・運動記録と日ごとの合計・運動消費
- `list_foods` : 登録食品と栄養値・お気に入りフラグ（食品名・店舗名のキーワードで絞り込み可）
- `list_sports` : 登録スポーツと消費の単位 METs
- `get_frequent_foods` : 直近 1〜365 日（既定 60 日）の記録を食品名（表記ゆれを正規化）ごとに集計し、回数順に回数・最後に食べた日・栄養値を返す。お気に入り食品も返す
- `log_meal` : 食べた物を1品ずつ食事記録に追加（日付・時刻は省略可。省略時は今日なら現在時刻、それ以外は 12:00）。記録後のその日の摂取状況を返す
- `log_activity` : 登録スポーツ名・強度・時間(分)を指定して運動記録に追加（消費カロリーは METs × 強度係数 × 体重 × 時間 × 1.05）。記録後のその日の摂取状況を返す

### 11.2 認証（OAuth 2.1）

- 本アプリが認可サーバーを兼ねる。クライアント登録は CIMD のみ、公開クライアント + PKCE (S256)
- `/oauth/authorize` は未ログインなら `/login` に誘導し、ログイン後に同意画面を表示
- 認可レスポンスには RFC 9207 の `iss` を付与。`resource`（RFC 8707）は指定時にこの MCP サーバーの URL と一致する必要がある
- アクセストークン 1 時間、リフレッシュトークン 90 日（使用ごとにローテーション）

### 11.3 食事の提案（アプリ内）

- 提案画面（`/suggest`、下部ナビ「提案」）の「今日の食事をまとめて提案してもらう」で、今日これからの食事（朝・昼・晩のうち、今の時間帯と、食べた物を割り当てた最後の食事の次のうち遅いほう以降。夜まで食べ終えていても夜は残す。`upcomingSlots`）を AI（OpenAI + Web 検索）に1回でまとめて提案させる。食事ごとに異なるお店で3案。全部食べると残りをちょうど使い切る配分にする
- AI に渡すもの: 今日の上限・摂取済み・残り、今日食べた物、直近10日の食事、予定（出社/在宅/休み・勤務時間）と居場所の推定、端末の現在地と最寄り駅、周辺のお店（OpenStreetMap）、栄養を公開している主なチェーン（`lib/chain-stores.ts`）、近くのお店の公式の栄養成分での組み合わせ候補（下記）、今日の予定・気分、食の好み
- 食の好み（設定画面「食の好み」、`pfc_user_settings.meal_preferences_json`）: AI への指示（メニュー選びのルールとしてそのまま渡す自由記述。既定値は `lib/meal-instructions.ts` で「既定に戻す」で戻せる。苦手な食材などもここに書く）と、お店ごとの定番メニュー・注文のしかた（そのお店を提案するときに従う）。店名は主なチェーンと食品辞書・記録の店名から候補を出す。MCP の `get_nutrition_status` にも `mealPreferences` として含める
- 居場所の推定（`lib/meal-schedule.ts` の `planMeal`）: 出社日の朝は自宅→会社の通勤路、昼は会社、夜は会社→自宅の帰り道。在宅勤務・休みの日は自宅周辺
- メニュー選び: 今日・昨日食べた物は避け、2日以上前に食べた物は積極的に候補にする。コンビニの新商品は Web 検索で調べて積極的に入れる。最後の食事では残りをちょうど使い切る量にする
- 公式の栄養成分での組み合わせ候補: 近くのお店（「お店を選ぶ」で選んだときはそのお店）のうち商品カタログ（11.4）のあるお店ごとに、この食事の目安（残りを朝昼晩の配分で分けた量）に近い組み合わせを3案、機械的に選んで AI に渡す。店名にカタログのお店の名前を含めばそのお店（コンビニはメーカーの既製品も合わせる）、カタログの無いコンビニ・スーパーがあればメーカーの既製品だけの候補も渡す。AI にはこれらのお店ではこの商品を優先し、商品名をそのまま使わせる。AI が返した商品名が候補の商品と一致したら、栄養値は公式の値に置き換える
- AI なしの組み合わせ: 提案画面の「お店の商品から組み合わせる（AI なし）」でお店と食事を選ぶと、11.4 の組み合わせ提案 API で5案をすぐに出し、各案を「記録する」で記録できる。メーカーの既製品は商品名にメーカー名を付ける
- 応答の形は Structured Outputs（JSON Schema）で固定し、栄養値は必ず数値で返させる。公式の栄養成分が見つからない商品は一般的な分量・栄養値から推定させる
- 朝昼晩の上限カロリー: 提案画面のバーの2本の線を動かして、1日の上限カロリーを朝・昼・晩に分ける（既定は朝20%・昼40%・夜40%。「既定に戻す」で戻せる）。日ごとに自動保存し（`pfc_meal_splits`、`PUT /api/meal-split`）、AI の提案・AI なしの組み合わせ・朝の通知すべてで、今日の残りをこの比率で分けた量を各食事の上限にする。食べた分は、あとの食事の上限に反映される（残りをあとの食事の配分で分け直す）。食べた物を割り当て済みの食事（3.3.0）は食べ終えたとみなして配分から外し、その食事をあらためて提案させるときは、食べた分も含めて分けたうえで差し引いた食べ足す分を上限にする（`lib/meal-split.ts` の `targetFor`）。提案画面の各食事の見出しにこの上限（「あと○kcal」）を出す。AI には今日食べた物それぞれの食事枠も渡す
- 今日の予定・気分: 提案画面の入力欄に書くと日ごとに自動保存し（`pfc_meal_notes`）、その日の提案（まとめて・食事ごとのやり直し・朝の通知）すべてで AI に渡す。翌日は空の状態から書く
- 提案し直しは食事ごと: 各食事の「別の案」で前回と違うお店・メニューにやり直し、「お店を選ぶ」で選んだお店だけから提案させる。まだ提案の無い食事は「提案してもらう」でその食事だけ提案させる
- 各案の「記録する」で全品を現在時刻で食事記録に追加
- 提案はやり直した分も含めてすべて保存（`pfc_meal_suggestions`）。画面では最新を上に、前の提案を折りたたんで下に残し、「別の案」ではその日その食事枠で出した案すべてを避けさせる。現在地は提案時に保存し（`pfc_user_locations`）、18時間以内なら定期実行でも使う。食事（朝・昼・晩）ごとに見出しを押すと折り畳め、畳んでいる間は最新の提案のお店名（考え中はスピナー）を見出しに出す
- Google カレンダー連携（設定画面「Google カレンダー」、`lib/server/google-calendar.ts`）: 連携すると今日の予定（時間・タイトル・場所、終わった予定には印）を「今日の予定と居場所」に加える。`calendar.readonly` を追加で同意させ、リフレッシュトークンを `accounts` に保存するので定期実行の通知でも使える。取得に失敗したら予定なしで提案を続ける。「連携を解除」で Google 側の許可も取り消す
- Kalori 連携（設定画面「Kalori」、`lib/server/kalori.ts`）: Kalori（kalori.jp）の MCP サーバーに OAuth（認可コード + PKCE、`kalori.read` のみ）で接続する。連携のたびにクライアントを動的登録し、リフレッシュトークンを `kalori_connections` に保存して、期限が近いアクセストークンを取り直す。リフレッシュトークンが失効していれば連携を消す。「連携を解除」で Kalori 側のトークンも失効させる。食事を記録するシートの検索（`components/record/AddFoodDrawer.tsx`）で、過去の記録・食品リストに当てはまるものが無いときに `GET /api/catalog-search` を引く。公式サイトから集めたカタログ（`data/*.json`）を先に探し、1 件も無ければ連携済みの場合に限って Kalori の `search_foods`（MCP、`@modelcontextprotocol/client`）を引く。結果の栄養値は公式値と AI 推定値が混ざり、区別はしていない
- 通知: 設定画面でオンにすると毎朝 7:00 ごろに今日の朝昼晩の提案をまとめて作って Web Push で通知し、タップで提案画面を開く

### 11.4 商品の組み合わせ提案 API（AI なし）

- `GET /api/combination-suggestions?store=seven-eleven&slot=lunch`（要ログイン。`store` は `lib/catalog/stores.ts` のコンビニ・飲食店の店舗 ID か、メーカーの既製品だけから組み合わせる `grocery`（スーパー・ドラッグストア）、`slot` は `breakfast` / `lunch` / `dinner` で省略時は今日これから食べる最初の食事）で、そのお店の商品から目標に近い組み合わせを最大5案返す。応答は `{ store, slot, target, combinations: [{ items, total, price }] }`。`items` は商品名・カテゴリ・税込価格・販売地域・PFC・公式サイトの URL（価格・販売地域はお店により無し）

## 12. PWA / アプリ配布関連

- Web App Manifest により standalone 表示対応
- Service Worker は Serwist（`app/sw.ts`、`/serwist/sw.js` で配信）。`/api/*` はキャッシュしない
- アイコン（192 / 512）設定
- Android TWA プロジェクトを同梱（`twa/`）

## 13. プライバシー・データ取り扱い

- 食事ログや設定はログインユーザー単位でサーバーに保存
- 取得情報は機能提供（計算・表示・入力補助）に利用
- 法令等を除き第三者提供しない方針
- ChatGPT 等の外部アプリには、ユーザーが同意画面で許可した場合に限り読み取りを許可する
